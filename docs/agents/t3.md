# T3 — template render engine

## What was built

Files added under `lib/render/` (the only files this task owns):

- `lib/render/index.ts` — public entry point, `renderResume({ templateContent, library, selections })
  -> { tex, warnings }`. Pure/synchronous, no I/O, no DB imports. Delegates to `sections.ts` for the
  four expansions and to `tokens.ts` for substitution, then returns the combined warnings list.
- `lib/render/tokens.ts` — `substituteTokens(template, values, warnings)`, matching
  `/<<([A-Z_]+)>>/g` per `docs/TEMPLATE_TOKENS.md`. Known tokens are substituted at every
  occurrence; unknown tokens are left verbatim in the output, with one warning per distinct
  unknown token name (not one per occurrence, to avoid spamming the warnings list when the same
  typo appears twice).
- `lib/render/sections.ts` — the four expansions:
  - `renderExperiences` / `renderProjects`: walk `selections.experiences` /
    `selections.projects` in array order (array index = order, per the `Selections` contract),
    resolve each id against the library, resolve its selected bullets in order, and emit
    `\resumeSubheading{...}` / `\resumeProjectHeading{...}` plus a `\resumeItemListStart/End`
    block — omitted entirely when there are zero selected bullets (an empty `itemize` is a LaTeX
    error). Dangling experience/project/bullet ids push a warning and are skipped, never thrown.
    `isArchived` is never read anywhere in this file.
  - `renderSkills`: a single pass over `selections.skillRows` that resolves each row's selected
    skills and buckets the resulting `\textbf{Name}{: a, b, c}` line into a `top` or `bottom`
    array based on **the row's own `top` flag** (not on which of `<<SKILLS_TOP>>` /
    `<<SKILLS_BOTTOM>>` a caller happens to be building) — this is what makes it impossible for a
    row to land in both sections. Rows with zero selected skills are skipped with a warning.
    Doing top/bottom together in one function also means a dangling row/skill id only warns once,
    rather than once per section.
- `lib/render/default-template.ts` — exports `DEFAULT_TEMPLATE`, a `String.raw` template literal
  containing `docs/reference/v1-resume.tex` byte-for-byte except:
  - the three `\resumeSubheading{...}` blocks in Experience replaced by `<<EXPERIENCES>>`
  - the three `\resumeProjectHeading{...}` blocks in Projects replaced by `<<PROJECTS>>`
  - the three `\textbf{Languages}` / `\textbf{Frameworks...}` / `\textbf{Cloud Technologies}`
    lines replaced by `<<SKILLS_TOP>>`
  - the two `\textbf{Interests}` / `\textbf{Accolades}` lines replaced by `<<SKILLS_BOTTOM>>`

  Everything else — preamble, macros, the commented-out alternate header/font options, the
  centered header, and Education — is untouched, including blank lines and comments, since this
  is the user's real resume and T5/the user will keep hand-editing it. `String.raw` is used
  (rather than a normal template literal or a `.replace()`-built string) specifically so that the
  literal backslashes in `\textbf`, `\resumeItem`, `\%`, `\&`, etc. survive unmangled — a plain
  template literal would interpret `\t` inside `\textbf` as a tab character, silently corrupting
  the template. I verified this behavior mismatch experimentally before committing to the
  approach (see "Deviations" below for the tsconfig implication of using extensioned imports —
  unrelated micro-issue, noted separately).
- `lib/render/render.test.ts` — 17 `node:test` tests (`node:test` + `node:assert/strict`), listed
  below.

## The v1 round trip — the project's smoke test

The round-trip test builds `v1Library` / `v1Selections` fixtures that transcribe the exact
content of `docs/reference/v1-resume.tex` (3 experiences with 4/5/5 bullets, 3 projects with 2
bullets each, 3 top skill rows, 2 bottom skill rows — every id fully selected, in file order),
renders them against `DEFAULT_TEMPLATE`, and:

1. asserts `warnings` is empty (a clean render of real content should never warn),
2. writes the rendered tex to `lib/render/.scratch/v1-round-trip-output.tex` (gitignored; run the
   test locally to regenerate it),
3. normalizes insignificant whitespace on both sides (per-line trim + collapsing runs of spaces —
   justified because LaTeX's tokenizer discards leading spaces at the start of every line and
   collapses interior whitespace runs to one space; this has no effect on the compiled document),
4. asserts equality against the reference file **after applying two explicit, narrowly-scoped,
   commented substitutions** for the two known/expected divergences below — if either divergence
   line has since changed or vanished from the reference file, the test fails loudly rather than
   silently passing.

### Line-by-line explanation of every diff hunk

1. **Leading space per skills line, single→double space after `:` on the Languages row.**
   Insignificant: TeX's tokenizer is in "state N" at the start of every line and skips leading
   spaces there, and consecutive interior spaces collapse to one in horizontal mode either way.
   The renderer always emits exactly one space after `:` per the contract's shown row format
   (`\textbf{Name}{: a, b, c}`); the hand-authored reference has a stray double space on one row.
   Covered by the round-trip test's `normalizeInsignificantWhitespace`.
2. **The commented-out placeholder bullet is missing from the render.** This is a genuine,
   expected, and permanent divergence, not a bug: `% \resumeItem{Built ...}` is a LaTeX comment
   the original author left as a note-to-self inside Experience #1's bullet list. LaTeX comments
   have zero effect on the compiled document, and there is no way for a data-driven renderer to
   reproduce "a comment living inside token-owned, fully-regenerated content" — the entire bullet
   list for that experience is emitted from `Selections`/`Library`, which has no concept of
   dead/commented entries. The round-trip test asserts this exact line is present in the
   reference and then removes it before comparing, so the test still fails loudly if any *other*
   line goes missing.
3. **`$|$`-separated vs comma-separated Additional Information rows.** `docs/TEMPLATE_TOKENS.md`
   says skills are comma-separated within a row for **both** `<<SKILLS_TOP>>` and
   `<<SKILLS_BOTTOM>>`, with no mention of a per-row or per-section separator override. The
   hand-authored reference resume predates that frozen contract and instead separates the
   Interests/Accolades values with `$|$` (the same glyph used between header contact links). Per
   the task's instruction to "implement [the contract] exactly," the renderer always emits commas
   here; matching the reference's pipe style would mean inventing an undocumented per-row
   separator concept that isn't in the contract. The round-trip test documents this explicitly
   and substitutes the two known pipe-separated strings for their comma-separated equivalents
   before comparing (again asserting the pipe form is present first, so it fails loudly if the
   reference file changes). If this needs to be fixed for real, the fix belongs in the reference
   resume's content (re-enter Interests/Accolades with commas) or in a future amendment to
   `TEMPLATE_TOKENS.md`, not in the renderer.

No other differences exist. In particular the trailing single space before the closing brace on
`Racket }` and `Vercel }` in the reference file is reproduced exactly — I transcribed those as
literal trailing characters on the last skill name in each of those two rows (`"Racket "`,
`"Vercel "`) rather than normalizing them away, since D-008 treats content as verbatim and this is
exactly the kind of stray-but-real character a real user's data would contain.

## Deviations from the contract / notes

- **`tsconfig.json`**: added `"allowImportingTsExtensions": true`. This was necessary, not
  optional: the task's own verification commands require both `npx tsc --noEmit` (using
  `moduleResolution: "bundler"`, which — like the rest of Next.js — normally forbids `.ts` file
  extensions in import specifiers) *and* `node --test --experimental-strip-types
  lib/render/render.test.ts` (Node's ESM resolver requires an explicit extension for every
  relative import — I verified this fails with `ERR_MODULE_NOT_FOUND` otherwise). The only way to
  satisfy both simultaneously is extensioned relative imports (`from './sections.ts'`) plus this
  flag, which TypeScript only permits when `noEmit` is set (already true here) and has no runtime
  or bundler effect — it only relaxes the type-checker's import-path validation. All imports
  within `lib/render/*.ts` use explicit `.ts` extensions for this reason; this is a one-line,
  narrowly-scoped, backward-compatible change (nothing else in the repo used relative imports
  before this task).
- **`.gitignore`**: added `lib/render/.scratch/` — the round-trip test writes its rendered output
  there for inspection; it's regenerated on every test run and isn't meant to be committed.
- No changes were made to `lib/types.ts`, `docs/TEMPLATE_TOKENS.md`, or
  `docs/reference/v1-resume.tex`.
- Unknown-token warnings are deduplicated per distinct token name (not per occurrence), to avoid
  flooding the warnings list if the same unknown token appears many times in a template. This is
  a judgment call the contract doesn't specify either way.
- `renderSkills` resolves both `<<SKILLS_TOP>>` and `<<SKILLS_BOTTOM>>` in a single pass (see
  above) specifically so dangling-id warnings aren't duplicated across the two sections and so
  the "exactly one place" requirement is structurally guaranteed rather than tested-for.

## Notes for T5 (seeding) and T6

- **T5**: `import { DEFAULT_TEMPLATE } from '@/lib/render/default-template'` (or a relative import
  with a `.ts` extension, consistent with this task) gives you the exact string to seed as the
  content of the default `Template` row. It is a plain string constant with no placeholders beyond
  the four `<<TOKENS>>`; nothing else needs to be filled in.
- **T6** (or whichever task wires up the actual render/preview flow): `renderResume` is a pure
  function — call it with `{ templateContent, library, selections }` sourced from
  `ResumeDetail`/`GET /api/resumes/:id` and it returns `{ tex, warnings }` synchronously. Feed
  `warnings` to the UI's warnings pane; feed `tex` to the LaTeX sidecar for compilation. It never
  throws on bad data (dangling ids, empty selections, etc.), so it's safe to call directly from a
  request handler without a try/catch dedicated to renderer bugs — LaTeX compile errors are a
  separate concern surfaced by the sidecar, not by this module.
- If a future task wants the reference resume's Additional Information section to round-trip
  byte-for-byte, that requires either re-entering that content with comma separators (matching
  the frozen contract) or amending `docs/TEMPLATE_TOKENS.md` to define a per-row/per-section
  separator — the renderer intentionally does not special-case this.
