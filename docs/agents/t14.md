# T14 — multi-user

Branch `feat/t14-multi-user`, worktree `../resumix-wt/t14`.

**Task id note.** This is T14, not T13: `../resumix-wt/t13` was already
occupied by an unrelated `feat/t13-feedback-widget` worktree.

## What was asked

Make the database multi-user before deploying, so that later features are
built on it rather than retrofitted onto it. Every row belongs to exactly one
user; users cannot see each other's data. Auth itself was explicitly out of
scope beyond a stub — Supabase OAuth comes later — but local development had
to keep working with no credentials. No cloud, no deployment.

## What was built

**Schema (`drizzle/0003_multi_user.sql`).** A `users` table, plus `user_id` on
the five root tables (`template`, `experience`, `project`,
`technical_skill_row`, `resume`). Children and bridge rows inherit their owner
through their parent — see D-018 for why they do not get a column of their
own. `ux_template_one_default` and `ux_resume_one_default` became per-user
partial unique indexes; without that, provisioning a second account would
collide on the first one's default.

The migration backfills. If any pre-existing rows are found it creates
`owner@localhost` and assigns them all, then sets the columns `not null`.
Verified both ways: a fresh database (0000→0003 + seed) and a simulated
pre-T14 database (0000→0002, old-style rows inserted, then 0003), which
adopted all five root tables' rows with nothing left orphaned.

**Session resolution (`lib/session.ts`).** One entry point, `requireUserId(request)`,
behind three modes (D-019):

- `dev` — no login; the session is the first user in `users`.
- `password` — the existing shared-password gate, but the token now carries a
  `sub` claim naming its user (D-020, token version 1 → 2).
- `supabase` — written, unreachable. `lib/auth-supabase.ts` throws until
  someone implements JWT verification; the mapping from a verified identity
  onto a `users` row (by `supabase_user_id`, falling back to email, else
  provisioning) is already written around it.

**Query layer.** Every function in `lib/queries/**` now takes a `userId` and
filters on it. Child rows are filtered through a join to their parent. The
selections writer re-checks every incoming content id against the caller —
that is the path that would otherwise let one user's experience be selected
onto another's resume, since bridge rows carry no owner.

**Seed.** `scripts/seed.ts` creates one user (`SEED_USER_EMAIL`, defaulting to
the address already in the reference resume's header) and loads the V1 resume
under it. That user is what `dev` mode logs in as, so a clean clone goes from
`db:seed` to a working app with nothing to configure.

## Deviations from the brief

1. **The password gate was kept, not replaced with the stub.** Deleting
   working, tested auth to install something that throws would have left no
   deployable path at all, and it is what the e2e suite logs in through.
   It is now one mode of three rather than the only option.
2. **`GET /api/session` was added** (a contract change to `docs/API.md`).
   `AuthGate` previously inferred "logged in" from a token in `localStorage`,
   which is wrong in dev mode, where a valid session has no token. The gate
   now asks the server.
3. **`getLatestResumePdfMetaByResumeId` was fixed while passing through.** It
   ignored its `resumeIds` argument and scanned every snapshot in the table,
   relying on the caller to pick out the rows it cared about. Harmless when
   one person owned the database; now both a cross-user smell and an
   unnecessary full scan. It filters properly.
4. **The browser suite now pins `RESUMIX_AUTH_MODE=password`**, so it keeps
   driving the real login screen instead of silently picking up the new
   `dev` default.

   Dev mode was first covered by a second Playwright `webServer` on :3101.
   That worked (19/19 green) but was reverted: two `next dev` processes
   cannot share `.next`, and giving the second one its own `distDir` made
   Next rewrite `tsconfig.json` and `next-env.d.ts` on every run — including
   silently dropping `allowImportingTsExtensions` — which would have left
   dirty tracked files after every merge-gate run. Dev and supabase modes are
   covered in-process instead by `lib/session.test.ts`, which calls
   `requireUser()` with real `Request` objects against a real database. That
   also buys coverage a browser test could not: that `supabase` mode fails
   closed, and that the password gate refuses to guess an account when
   several users exist.

## Verification

- `npx tsc --noEmit` — clean.
- `npm test` — 143 pass / 0 fail (run with `DATABASE_URL` set; without it the
  DB-backed suites skip as before). Includes 13 isolation tests, 12 session
  tests across all three auth modes, and 7 auth-mode tests.
- `npm run build` — green, 21 routes.
- `npm run smoke` — round trip + compile + empty-section cases all PASS. The
  V1 resume still reproduces byte-for-byte, now read back through a
  user-scoped query.
- `npx playwright test` — 16 passed, unchanged.

Everything ran against a dedicated `resumix_t14` database rather than the
shared `resumix` one, because another worktree was using the latter and this
migration would have broken its code.

## One trap worth knowing about

The `withEnv` test helper (copied from `lib/auth.test.ts`) restored
`process.env` in a **synchronous** `finally`, so an async function under test
that read an env var after its first `await` saw the restored value, not the
one the test set. It fails in one direction only — toward "returned null" —
so a "fails closed" assertion passes for entirely the wrong reason. Two real
failures in `lib/session.test.ts` exposed it; the helper now awaits inside
the try, in both files.

## Not done (deliberately)

- Supabase OAuth itself. The seam is `lib/auth-supabase.ts`; the checklist
  for implementing it is in that file's header.
- Any UI for switching or displaying the current user. Dev mode shows no
  indication of who you are signed in as, which is fine with one seeded user
  and worth revisiting when OAuth lands.
- Deleting a user. `on delete restrict` means it fails loudly rather than
  quietly cascading through content that "is never deleted" (D-011).
- Deployment, per the brief.
