# T10 — End-to-end coverage of the full user journey

## What was built

Eight new Playwright spec files under `e2e/`, one per spec.md promise listed in the task brief, plus
a shared support module. Every test drives a real Chromium browser against the real Next.js dev
server, real Postgres, and the real `latex` compile sidecar (per `playwright.config.ts` — no mocks).

### Files added

- `e2e/support.ts` — shared test infrastructure:
  - `login`, `createResumeViaUi` — drive the real password gate and the real "new resume" modal
    (not `window.prompt`, matching the app's actual implementation).
  - `getResumeDetail`, `findExperienceBullet`, `findExperienceId`, `createResumeViaApi`,
    `renderResumeText` — thin wrappers around the real API (called via `page.evaluate(fetch(...))`
    so they run same-origin with the browser's stored token), used only for **setup and
    verification** (finding a real id by a seeded item's stable name, confirming server-side truth)
    — every mutation a test is actually about goes through real UI interaction.
  - `extractPdfText` — decodes a base64 or on-disk PDF into plain text via `pdfjs-dist`'s
    `legacy/build/pdf.mjs` entry point (already a transitive dependency via `react-pdf`, so this
    adds no new dependency). Chosen over screenshot diffing or page-count-only checks because it
    lets tests assert *exact wording* is or isn't present — load-bearing for the anti-drift test
    (old vs. new PDF bytes) and the archive test (archived-but-selected content still renders).
  - `dragRowAbove` — a real `@dnd-kit` pointer drag: press the drag handle, move past the 4px
    `activationConstraint`, hover the target row, release. See "Discrepancies" below for why this is
    mouse-based, not keyboard-based, despite the task brief's suggestion.
  - `waitForSaved` — waits for the header's aggregate autosave badge to read "Saved", i.e. every
    autosave channel has actually landed server-side, before the next step depends on it.
- `e2e/create-clone.spec.ts`, `e2e/selection-scope.spec.ts`, `e2e/global-edit.spec.ts`,
  `e2e/reorder.spec.ts`, `e2e/archive.spec.ts`, `e2e/pdf-drift.spec.ts`, `e2e/filename.spec.ts`,
  `e2e/search.spec.ts` — one file per promise; see the table below.

### Files extended (minimal `data-testid` additions only, per the task's one allowed exception)

- `components/editor/ItemBulletSection.tsx` — `data-testid="content-row-<id>"` on each
  experience/project row, `data-testid="bullet-row-<id>"` on each bullet row. Needed because rows
  aren't otherwise addressable by a stable id from a test (only by their current, editable text).
- `components/editor/SortableRow.tsx` — `data-testid="drag-row-<id>"` on the row wrapper that
  actually contains the drag handle (the handle is a **sibling** of `ItemBulletSection`'s own
  `content-row-<id>` div, not a descendant of it — this tripped up the first version of
  `dragRowAbove` with a silent `boundingBox()` timeout until the testid was moved to the right
  element).
- `components/home/ResumeCard.tsx` — `data-testid="resume-card-<id>"` on the card,
  `data-testid="resume-download-button"` on its download button — needed to address one specific
  resume's card among many on the home grid, and to distinguish its download button from every
  other card's identically-labelled one.

No other application code was changed. No test asserts on anything the app doesn't actually do; two
early test-authoring bugs (a same-experience content substring colliding with another spec file's
global content edit, and the drag-handle/content-row DOM-sibling issue above) were fixed in the
tests/testids, not by changing app behavior.

## Discrepancies found between spec.md and the app

None of these are outright violations of spec.md's letter — spec.md leaves a lot of implementation
detail unspecified, and every actual *behavioral promise* it makes held up under test. Listed here
per the task's instruction to report "every discrepancy, however small":

1. **"Archive... disappears from the picker by default" is true only for content *not currently
   selected on the resume you're viewing*.** `lib/editor/visibility.ts`'s `isVisible` (D-011, from
   T8) keeps an archived-but-still-*selected* item visible in the picker even with "show archived"
   off, specifically so a user can still find and deselect it. spec.md's phrasing ("there should be
   a way to toggle to see archived content, but by default it should be hidden") doesn't
   distinguish this case, and the app's actual behavior is a **strictly safer superset** of the
   literal ask (nothing a resume references can ever become invisible-and-unremovable), not a
   regression — but it means `archive.spec.ts` has to check "hidden by default" on a resume that
   deselected the item and "still renders" on a *different* resume that kept it selected, rather
   than proving both claims on one resume. Documented, not fixed — this is the app behaving better
   than a literal reading, not worse.
2. **The editor's "Save PDF" button both saves *and* immediately downloads**, rather than only
   saving (leaving download to the home page's per-card button). spec.md's own wording separates
   the two ("on the home page each resume should have a download button" vs. "click the save button
   in the top right, it should resave") without explicitly forbidding the editor button from also
   downloading. This was already flagged by T8 (`docs/agents/t8.md`, Deviations) as an intentional
   choice ("a user clicking 'Save PDF' while looking at the editor wants the file, not just a
   database write"); T10 confirms it's still true and that it doesn't undermine the anti-drift
   guarantee (`pdf-drift.spec.ts` uses this exact button for both the "old" and "new" saved
   snapshots and gets the correct, distinct bytes each time).
3. **The "new resume" flow is an in-app modal, not `window.prompt()`.** spec.md says "it should
   prompt me for the name of the company" — read literally, `window.prompt`; the app uses a styled,
   focus-trapped dialog instead (T8's `NewResumeDialog.tsx`, by design, per its own doc comment).
   Functionally equivalent (asks for a company name before creating), just worth noting as a literal
   textual mismatch. `create-clone.spec.ts` drives the real modal, not a native prompt.
4. **Grid position of the Default card is not asserted by any new test.** spec.md is specific that
   Default should sit "immediately to the right of the blank one." Code review of
   `components/home/ResumeGrid.tsx` confirms the DOM order is `NewResumeCard`, then `ResumeCard
   (Default)`, then the rest — matching the spec — but no test in this task's scope asserts the
   *visual/DOM position* directly (only that both cells are present and, per `search.spec.ts`,
   remain visible under a search query). Flagging as an untested (not failing) claim.

No other discrepancies were found: content selection scoping, global content edits, drag-reorder
persistence, archived-but-selected rendering, the PDF anti-drift guarantee, and the exact filename
transform all match spec.md's promises exactly, verified against the real app (not mocks) in a real
browser.

## Notes on test technique

- **No `KeyboardSensor` is registered anywhere `@dnd-kit` is used**
  (`components/editor/SortableList.tsx` only wires up `PointerSensor`). The task brief's suggested
  approach (focus the handle, Space to lift, arrows to move, Space to drop) is therefore not
  available in this app as built — attempting it produces no drag at all, since `@dnd-kit`'s
  keyboard coordinate-getter is only invoked when a `KeyboardSensor` is one of the sensors passed to
  `useSensors`. `e2e/reorder.spec.ts` uses a real mouse-driven pointer gesture instead
  (`dragRowAbove` in `support.ts`), which the task brief explicitly permits as a fallback ("use
  mouse only if keyboard genuinely does not work"). This is not a spec violation (spec.md doesn't
  mention keyboard accessibility for drag-and-drop) — noting it here as a fact about the
  implementation that shaped the test, and as a possible small accessibility gap worth a follow-up
  task if keyboard-only reordering ever becomes a requirement.
- **PDF content assertions use real text extraction (`pdfjs-dist`), not screenshots or page counts.**
  This is what makes `pdf-drift.spec.ts` and `archive.spec.ts` unambiguous: they assert the actual
  wording present in a compiled PDF, not just "a PDF exists" or "it has N pages."
- **Tests are independent and reseed-safe.** Every test creates its own uniquely-named resume(s)
  (timestamped or randomized) rather than reusing a fixed fixture resume, and any test that performs
  a *global* content edit (bullet text, archiving) targets a different specific bullet than every
  other test that also edits globally, so no two spec files' global mutations can stomp on each
  other regardless of run order. Verified by running the full suite twice in a row against two
  separate `--force` reseeds (see verbatim output below) with identical results both times.
- One test run mid-development hit a transient `latex service returned 401: unauthorized` from the
  shared `resumix-latex-1` Docker container (the same shared container multiple worktrees bind to —
  see `docs/agents/t8.md`/`t9.md` for the same sharing situation). A direct `curl` against the
  service immediately after showed it healthy and unauthenticated (`LATEX_SERVICE_TOKEN` is unset in
  that container), and the affected test passed cleanly on retry and on both full-suite reruns
  logged below — almost certainly a moment of interference from another worktree touching the same
  shared container, not an application bug. Flagging in case it recurs.
