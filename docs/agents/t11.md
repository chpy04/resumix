# T11 — deployment path + developer documentation

Branch: `feat/t11-deploy` (worktree `../resumix-wt/t11`). Not merged, not pushed.

## What was built

- **`README.md`** — rewritten for someone who just cloned the repo: what the
  app is and the core idea (content is global, a resume is a selection +
  ordering), a verified quick-start, the full command reference, an
  architecture diagram, and pointers into `docs/`.
- **`docs/DEPLOYMENT.md`** (new) — the real path to production in three
  parts: Supabase (pooler connection string, port 6543, why `prepare: false`
  matters), the latex sidecar on Fly.io (deploy steps, scale-to-zero,
  locking it down), and Vercel (every env var, the render-timeout risk).
  Includes a pre-flight checklist and a troubleshooting section for the three
  failure modes named in the brief.
- **`services/latex/fly.toml`** (new) — a real, TOML-validated Fly config for
  the sidecar: scale-to-zero (`min_machines_running = 0`,
  `auto_stop_machines`/`auto_start_machines`), sized for TeX Live + a couple
  of concurrent compiles.
- **`CLAUDE.md`** (new, 90 lines) — architecture paragraph, the five-command
  merge gate, worktree/branch convention, where the contracts live and that
  they're authoritative, archive-never-delete, raw-unescaped-LaTeX, and the
  four traps named in the brief (Edge/`node:crypto`, page prop typing,
  lazy DB client, react-pdf client-only + local worker). Links into `docs/`
  rather than duplicating it.
- **`docs/CONTRIBUTING.md`** (new) — adding a migration, adding an endpoint,
  running the smoke test, and the rule that `SCHEMA.md`/`API.md`/
  `TEMPLATE_TOKENS.md` are contracts.
- **`package.json`** — small, real fix, not scope creep: `db:migrate`,
  `db:seed`, and `smoke` now run with `--env-file-if-exists=.env`. Without
  this, the README's own quick-start (`npm run db:migrate` right after
  `cp .env.example .env`) fails with `DATABASE_URL is not set`, because
  `.env` is only auto-loaded by `next dev`/`next build`, not by plain `node`
  scripts. Verified this was a real bug (reproduced the failure, then
  confirmed the fix) before touching the file — see "What was verified"
  below.
- **`services/latex/README.md`** — corrected its Fly.io section, which
  claimed the sidecar could stay fully private (`.internal`/Flycast only).
  That's only true if the Next.js app also runs on Fly; this project's actual
  target is Vercel, a different cloud that cannot join Fly's private
  WireGuard mesh, so a public Fly IP is actually unavoidable. Replaced the
  stale guidance with a short correction and a pointer to
  `docs/DEPLOYMENT.md` for the full story, rather than duplicating it here.

Files intentionally left alone: `docker-compose.yml` and `.env.example` — both
were already correct (checked by running the quick-start against them
end-to-end; no genuine problem found), so per the task brief they weren't
touched.

## What was verified (executed, not just read)

All of this was run for real, in this environment, against the already
running `resumix-db-1` / `resumix-latex-1` containers (the shared
docker-compose stack for this project — same `docker-compose.yml`, same
ports, confirmed byte-identical via `diff` against the main checkout's copy,
so testing against them is equivalent to testing against a fresh
`docker compose up -d db latex`):

- `cp .env.example .env`
- `npm install` (ran directly in the worktree to verify it actually works
  from a clean state; this replaces the `node_modules` symlink with a real
  local copy as a side effect of how `npm install` behaves — restored the
  symlink afterward, see note below)
- `npm run db:migrate` — **reproduced the `DATABASE_URL is not set` failure
  first**, then fixed `package.json` and confirmed it passes
  (`skip 0000_init.sql (already applied)`, `skip 0001_...`, "Nothing to do")
- `npm run db:seed` — confirmed the same fix applies; ran against an
  already-seeded DB (correctly reports "Already seeded... nothing to do")
- `npm run smoke` — full pass: round-trip match, `ok=true, pages=1`
- `npx tsc --noEmit` — clean
- `npm run build` — clean, **with no `.env` present** (confirms the lazy DB
  client claim in `lib/db/index.ts`/D-014 actually holds at build time, which
  the Vercel troubleshooting section in `docs/DEPLOYMENT.md` depends on)
- `npm test` — 89 passed, 16 skipped (DB-backed tests self-skip without a
  reachable `DATABASE_URL` in the test process's own env — expected), 0
  failed
- `npm run dev` — started, `GET /` and `GET /login` both 200,
  `POST /api/auth` with the seeded `.env`'s password returned a real token
- `services/latex/fly.toml` — validated as syntactically correct TOML via
  Python's `tomllib` (no `flyctl` available in this environment to do a
  deeper `fly config validate`)

Note on `npm install`: running it inside the worktree replaces the
`node_modules` symlink with a real local install (npm's behavior, not a bug
in this task) — confirmed the main checkout's `node_modules` was unaffected
(directory untouched, `du -sh` unchanged), then restored the worktree back to
a symlink afterward so the worktree is left exactly as it was received.

## Known gap surfaced, not fixed here

The latex sidecar has no authentication of its own (per
`services/latex/README.md`'s Security section), and — as worked out while
writing `docs/DEPLOYMENT.md` — a public Fly IP is unavoidable once the caller
is a Vercel serverless function (Vercel cannot join Fly's private 6PN mesh).
The most robust fix is a small shared-secret bearer-token check added to
`services/latex/server.js` (T2's file) and `lib/latex.ts` (T6's file, under
`lib/**`, which this task was told not to touch). Documented as a concrete,
scoped follow-up in `docs/DEPLOYMENT.md`'s "Locking it down" section rather
than implemented here.
