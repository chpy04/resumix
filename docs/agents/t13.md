# T13 — in-app feedback widget → GitHub issue

Branch: `feat/t13-feedback-widget` (worktree `../resumix-wt/t13`).

## Why

The app is about to be deployed and is maintained by AI agents pulling work
off GitHub. Filing an issue by hand every time something looks wrong in the
UI is the step that doesn't survive contact with real use, so the app files
them itself. This task is only the **push** half — an agent that reads issues
back off GitHub, fixes them, and deploys is separate work and deliberately
not in this repo.

## What was built

- **`components/feedback/FeedbackWidget.tsx`** — the floating "Give feedback"
  button (bottom-right, every authenticated page) plus the network call and
  submit/error/result state.
- **`components/feedback/FeedbackDialog.tsx`** — the form: two mutually
  exclusive circles (Bug / Feature request), a description textarea, a
  screenshot dropzone (drop, click-to-browse, **or ⌘V paste** — the clipboard
  is where a macOS screenshot actually lands), the captured page URL, and a
  success panel linking the issue it just opened.
- **`app/api/feedback/route.ts`** — `POST /api/feedback`, `multipart/form-data`.
  Thin, like every other handler: parse form → zod → `fileFeedback`.
- **`lib/feedback/issue.ts`** — pure issue formatting (title, body, labels,
  screenshot path). No network, no env, so it is fully unit-tested.
- **`lib/feedback/github.ts`** — the only module that talks to GitHub.
- **`lib/feedback/submit.ts`** — orchestration between the two.
- **`lib/feedback/screenshot-client.ts`** — browser-side downscaling.
- Mounted in `components/AuthGate.tsx` so it appears once, on every gated
  page, without each page opting in.

## Decisions worth knowing

1. **Screenshots are committed to an orphan branch, not "attached".** GitHub's
   issue API has no attachment endpoint — the web UI's drag-and-drop uploader
   is not public API. So the bytes go to `feedback-assets` (an orphan branch
   with no relation to code history) via the **Git Data API**, and the issue
   body links the raw URL *at that commit's sha*, which makes the link
   immutable. The Contents API would have been one call instead of five but
   caps a file at 1 MB, well under a Retina screenshot. This works because
   the repo is public: GitHub's image proxy can fetch the raw URL, so the
   screenshot renders inline in the issue. **If the repo is ever made
   private, inline rendering breaks** and the screenshot would need to be
   hosted by the app instead.
2. **Multipart, not JSON.** Base64 inside JSON inflates an image ~33% against
   Vercel's 4.5 MB request-body ceiling. The widget also downscales anything
   over 1 MB to ≤1600px and re-encodes as **PNG, not JPEG** — these are
   screenshots of text, and JPEG ringing around glyphs destroys exactly the
   detail a bug report exists to preserve.
3. **A failed screenshot upload does not fail the report.** The typed
   description is the valuable part; if the upload throws, the issue is still
   filed, the body says the screenshot couldn't be uploaded and why, and the
   response carries `screenshotUploaded: false` so the UI can say so too.
4. **Labels are best-effort.** A repo with no `feedback` label can 422 the
   whole issue; `createIssue` retries once, unlabelled, rather than losing it.
5. **Fails closed on missing config.** No `GITHUB_TOKEN`/`GITHUB_REPO` → 503
   with a clear message. The one thing a feedback button must never do is
   silently succeed.
6. **Mounted behind the password gate.** On the login screen the widget could
   only ever produce a 401, so it isn't offered there.
7. **The description is inserted into the issue body unescaped**, for the same
   reason as D-008: the author is the repo owner and meant the markdown (and
   LaTeX) they typed. The *URL* is escaped, because it isn't author prose — an
   unencoded `)` would end the markdown link early.

## What was verified

- `npx tsc --noEmit`, `npm test`, `npm run build`, `npm run smoke`,
  `npx playwright test` — all five green.
- New unit tests: `lib/feedback/issue.test.ts` (formatting, truncation,
  URL escaping, screenshot paths) and `lib/feedback/github.test.ts` (config
  parsing, the five-call upload sequence for both the existing-branch and
  first-ever-orphan cases, base64 encoding, the 422 label retry).
  `github.test.ts` stubs `globalThis.fetch`, so no test touches the network.
- `e2e/feedback.spec.ts` — three browser tests driving the real widget with
  `POST /api/feedback` stubbed at the network boundary: a bug report with a
  screenshot puts kind/description/page URL/file on the wire; a feature
  request from the editor records *that* page's URL and sends no file part;
  the form can't be submitted empty and isn't offered before login.
- **Live GitHub path, for real** (issue #1, since closed): a screenshot of the
  running app was posted to the real `POST /api/feedback` on a dev server with
  a live token. Confirmed afterwards via the GitHub API: the issue was labelled
  `feedback` + `bug`; `feedback-assets` was created with **0 parents** (a true
  orphan) containing only `screenshots/`; the raw URL in the body returns
  `200 image/png`, so it renders inline. A second upload was then run directly
  through `uploadScreenshot` (no issue filed) to prove the *append* path every
  later report takes — its commit's parent is the first commit, and the branch
  was afterwards rewound to that first commit, which the already-filed issue's
  screenshot survived unharmed because its URL is pinned to a sha.
