# T1 — Drizzle schema + migrations

Branch: `feat/t1-db-schema` (worktree `../resumix-wt/t1`). Not merged, not pushed.

## What was built

- `lib/db/schema.ts` — Drizzle `pgTable` definitions for all 15 tables in
  `docs/SCHEMA.md`: 7 content tables (`template`, `experience`,
  `experience_bullet`, `project`, `project_bullet`, `technical_skill_row`,
  `technical_skill`), `resume`, all 6 bridge tables, and `resume_pdf`.
  Exports inferred `*Record` / `New*Record` types for every table (named
  `Record`, not `Row`, to avoid a name collision between
  `technical_skill_row` the table and "a row of the table").
- `lib/db/index.ts` — `postgres.js` client + `drizzle-orm/postgres-js`
  singleton, reading `DATABASE_URL`, cached on `globalThis` so Next dev HMR
  doesn't leak connections.
- `drizzle/0000_init.sql` — hand-written SQL migration matching `schema.ts`
  exactly: table DDL, the shared `set_updated_at()` trigger function applied
  to every table via a per-table trigger, the two partial unique indexes
  (`ux_template_one_default`, `ux_resume_one_default`), composite PKs on all
  six bridge tables, `on delete cascade` on bridge FKs, `on delete restrict`
  on content-side FKs (experience_bullet→experience, project_bullet→project,
  technical_skill→technical_skill_row, resume→template), and secondary
  indexes (`experience_bullet.experience_id`, `project_bullet.project_id`,
  `technical_skill.technical_skill_row_id`, `resume.template_id`,
  `resume_pdf(resume_id, created_at desc)`). No `pgcrypto` extension — PG17
  has `gen_random_uuid()` built in, per the contract's own suggestion.
- `scripts/migrate.ts` — creates `_migrations(filename primary key,
  applied_at)` if missing, then applies any `drizzle/*.sql` file not yet
  recorded there, in filename order, each inside `sql.begin(...)` (one
  transaction per file, including the `insert into _migrations`). Re-running
  is a no-op for already-applied files.

Note: `drizzle/0000_init.sql` itself contains no `begin;`/`commit;` — the
migration runner owns the transaction boundary, not the SQL file (nesting
`begin`/`commit` inside a driver-managed transaction would commit early and
break the `_migrations` bookkeeping insert).

## Deviations from the contract, and why

- None to the table/column shapes in `docs/SCHEMA.md`. D-006 (the
  `technical_skill.technical_skill_row_id` FK not in the original spec) is
  already baked into `SCHEMA.md` itself, so this isn't a deviation on my
  part — I just implemented it.
- The contract doesn't specify `on delete` behavior for content-side FKs
  (`experience_bullet.experience_id`, `project_bullet.project_id`,
  `technical_skill.technical_skill_row_id`, `resume.template_id`) — only
  bridge-table FKs are specified as `on delete cascade`. Since D-011 says
  content is never deleted, this is moot in practice; I chose `on delete
  restrict` for all four so an accidental `DELETE` from the DB console fails
  loudly instead of silently orphaning/cascading child content. This is a
  judgment call, not a spec requirement — flag if you disagree.
- The contract doesn't state `not null` on `experience.company/title/
  date_range/location`, `project.name/technologies/date_range`, or
  `technical_skill_row.name` / `technical_skill.name` the way it does for
  `template.name`/`content`. I made them all `not null` (no default) because
  (a) `lib/types.ts` declares these as required non-optional strings, and
  (b) `docs/API.md`'s `POST /api/experiences` / `POST /api/projects` /
  `POST /api/skill-rows` bodies require all of those fields on creation, so
  there's never a code path that needs to insert a row without them.
- `resume_pdf` gets `updated_at` (with the same trigger) even though
  `SCHEMA.md`'s table only lists `created_at`. Requirement 3 in the task
  brief says "every table" gets both `created_at`/`updated_at`, and
  `resume_pdf` is immutable in practice, so `updated_at` will just always
  equal `created_at` — harmless, and keeps every table uniform for tooling
  that assumes both columns exist.
- Bridge tables get `created_at`/`updated_at` too, as explicitly called for
  in requirement 3 ("Bridge tables also get timestamps for consistency"),
  even though `SCHEMA.md`'s bridge-table section only lists the FK columns
  and `sort_order`.

## For the next agent

- `DATABASE_URL` for local dev: `postgres://resumix:resumix@localhost:5433/resumix`
  (docker-compose `db` service, host port 5433 — 5432 is often taken).
- Import the DB from server-only code as `import { db } from '@/lib/db'` and
  table/type defs as `import { resume, template, ... } from '@/lib/db/schema'`.
  Nothing under `components/**` should import either, per
  `docs/ARCHITECTURE.md`.
- `bytea` (`resume_pdf.bytes`) is modeled with a small `customType` in
  `schema.ts` (`{ data: Buffer; driverData: Buffer }`) since drizzle-orm's
  pg-core has no built-in bytea column builder. `postgres.js` hands bytea
  back as a Node `Buffer` by default, so reads/writes are just `Buffer`s —
  no base64 juggling needed in `lib/storage.ts`.
- `npm run db:migrate` (already wired in `package.json` from Wave 0) runs
  `scripts/migrate.ts`. Add new files as `drizzle/0001_*.sql`,
  `drizzle/0002_*.sql`, etc. — the runner sorts filenames lexically, so keep
  the zero-padded numeric prefix.
- No seed data was inserted by this task; `scripts/seed.ts` (T-whatever owns
  it — see `docs/WORKPLAN.md`) starts from a genuinely empty schema.
- I did not run `docker compose up -d latex` since it's out of scope for T1;
  only the `db` service was needed for verification.

## Contract problems found

None that block T1. The two judgment calls above (content-FK `on delete`
behavior, and `not null` on text columns the contract didn't explicitly mark)
are worth a quick nod from whoever reviews this, but neither contradicts
`docs/SCHEMA.md` — they fill gaps it left open.
