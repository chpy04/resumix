# T8 — Resume editor: shell + content pane

## What was built

The full editor screen at `/resume/[id]`: the two-tab header (Content / Template, tab state lifted
into the page for T9), the resizable two-pane layout, the entire Content tab (Experiences, Projects,
Technical Skill Rows — select/deselect, drag-and-drop reorder, expand to bullets/skills, inline
field editing, add/archive), the autosave plumbing, and a placeholder seam for T9's live PDF preview
and Template tab.

### Files added

- `app/resume/[id]/page.tsx` — server component: unwraps the async `params`, wraps
  `ResumeEditor` in the existing `AuthGate`.
- `lib/editor/selections-reducer.ts` + `.test.ts` — pure reducer for a resume's `Selections`.
  Encodes the one non-obvious rule in the API contract: `PUT /selections` replaces a whole slice
  (docs/API.md — "replaces each provided slice wholesale"), so for the three nested slices
  (`experienceBullets`, `projectBullets`, `skills`) an edit to one parent's children must still
  save the *entire* map, not a per-parent fragment. `affectedSlice(action)` always returns one of
  the six top-level `Selections` keys for exactly this reason. 21 `node:test` cases.
- `lib/editor/visibility.ts` + `.test.ts` — the D-011 "archived is hidden unless selected on this
  resume" rule (`isVisible`/`visibleItems`), plus the merged-ordering helpers that let one
  drag-and-drop list mix selected and unselected items (`orderForDisplay`,
  `extractSelectedOrder` — selected items pinned to the top in resume order, everything else below
  in library order; only the selected subset of a post-drag order is ever persisted). 12 cases.
- `lib/editor/autosave.ts` + `.test.ts` — `createAutosave`: a debounced, coalescing save queue
  (one in-flight request per queue, never parallel, trailing-edge coalescing so a burst of
  `schedule()` calls only ever sends the latest value), plus `combineStatuses` to fold several
  named queues into the one honest status shown in the header. 11 cases, using real (short) timers
  rather than a timer-mocking library, matching the rest of the project's plain `node:test` style.
- `components/editor/ResumeEditor.tsx` — the page's orchestrator: loads
  `GET /api/resumes/:id` once, owns `library`/`selections`/`resumeName` state, wires every mutation
  through either the selections reducer+autosave or a per-entity autosave channel (see below), owns
  tab state and the resizable divider, and renders load/error states.
- `components/editor/EditorHeader.tsx` — back link, editable resume name, the Content/Template
  tabs, the combined `SaveStatusBadge`, and the "Save PDF" action (`POST /pdf` then
  `GET /pdf`-download, both already in `lib/api-client.ts`).
- `components/editor/ContentPane.tsx` — composes the four sections (Experiences, Projects,
  Technical Skills top, Additional Information bottom) and the one "show archived" toggle + the
  persistent inline note explaining the per-resume-vs-global distinction (requirement 4).
- `components/editor/ItemBulletSection.tsx` — generic parent+bullets section, parameterized by a
  small `FieldSpec[]` per content type, used for both Experiences and Projects (their shape —
  `{ id, isArchived, bullets: Bullet[] }` plus a handful of string fields — is identical enough
  that a generic component was worth it; skill rows were not, see below).
- `components/editor/SkillsSection.tsx` — technical skill rows + skills, split by the `top`
  boolean into two section instances ("Technical Skills" / "Additional Information"). Kept
  separate from `ItemBulletSection` rather than forced into the same generic: children are
  name-only (no bullet content, no monospace/raw-LaTeX treatment), and rows carry `top`/`separator`
  fields the other two content types don't have.
- `components/editor/SortableList.tsx` / `SortableRow.tsx` / `DragHandle.tsx` — one `@dnd-kit`
  `DndContext`+`SortableContext` per list (no cross-list dragging is needed anywhere in the app, so
  each list — a section's items, or one item's bullets — gets its own independent context rather
  than one global one).
- `components/editor/atoms.tsx` — small shared, presentation-only pieces: `SelectToggle` (the
  on/off-this-resume checkbox), `GlobalEditBadge` (the "⊕ edits apply everywhere" tooltip icon —
  requirement 4's "inline note or icon"), `ArchivedBadge`, `ArchiveButton` (never a delete button —
  requirement 8), `ExpandChevron`.
- `components/editor/useAutosaveRegistry.ts` — a small React hook wrapping `createAutosave`:
  one named `AutosaveController` per key, created once and reused across renders (the `save`
  closure is refreshed every render via a ref so cached controllers always call current
  state/props without losing their in-flight/coalescing state), plus `combineStatuses` folded into
  one `status` and a `retryAll()` for the header's retry button.
- `components/editor/PreviewPanePlaceholder.tsx`, `TemplateTabPlaceholder.tsx` — the two seams
  for T9; see `docs/agents/t8-seams.md` for exactly what to replace and what's already lifted for
  them to use.

### Files extended

- `lib/api-client.ts` — added `getResumeDetail`, `updateResume`, `updateSelections`,
  `saveResumePdf`, and full create/update coverage for experiences, experience bullets, projects,
  project bullets, skill rows, skills, and templates (`updateTemplate`, for T9). Every new function

## How the "per-resume vs. global" distinction is surfaced (requirement 4)

This was called out as the single most important conceptual point, so three separate layers:

1. A persistent one-line note at the top of the Content pane: "Checkboxes and drag order save to
   **this resume only**. Editing text, adding, or archiving (⊕) changes it **everywhere**."
2. A small `⊕` icon (`GlobalEditBadge`) next to every row's text fields, with a `title` tooltip
   ("Edits here apply to every resume").
3. The archive button's own tooltip: "Archive (global) — there is no delete."

## Autosave design (requirement 5)

Two debounce tiers, both going through `lib/editor/autosave.ts`'s `createAutosave`, registered via
`useAutosaveRegistry` so they share one combined status:

- **Immediate (`debounceMs: 0`)**: all six selection slices (toggle/reorder) and every archive
  toggle. "Immediate" here means the first change in a burst fires right away; if further changes
  land while that request is still in flight, they coalesce into a single trailing request rather
  than queuing up or firing in parallel — see the `autosave.test.ts` "coalesces bursts" case.
- **Debounced (`debounceMs: 500`)**: every text field (experience/project/skill-row fields, bullet
  and skill content) and the resume's own name. Per-entity field edits are merged into one PATCH
  per entity (a `useFieldDrafts` ref merges e.g. `company` and `title` typed within the same
  500ms window into one `{ company, title }` body) rather than one PATCH per keystroke per field.
- **Failure handling**: a failed save never disappears silently — the queue's status flips to
  `'error'` and the header shows "Save failed — retry" (`SaveStatusBadge`), wired to
  `autosave.retryAll()`, which resends every channel's last-attempted value. A fresh edit after a
  failure supersedes the failed value on its own channel (the newer state is a strict superset of
  intent) but the failure is always shown before that happens.

## D-011 (archived-but-selected content stays visible) — requirement 6

`GET /api/resumes/:id` always returns the full library including archived rows (per
`docs/agents/t6.md` Deviations #4 — the resume-detail endpoint calls `assembleLibrary(true)`
unconditionally; only the standalone `GET /api/library` respects `?includeArchived`). `ContentPane`
and its sections filter client-side via `lib/editor/visibility.ts`'s `isVisible`/`visibleItems`:
archived items are hidden unless "show archived" is on, **or** the item is in the resume's own
selected-id set at that level — verified against the real API in manual testing (see below) and
covered by 4 of the 12 `visibility.test.ts` cases.

## Deviations from a literal reading of the brief

- **Task field-edit granularity**: rather than one autosave channel per text field, edits to
  multiple fields of the same entity within one 500ms window are merged into a single PATCH body
  (`useFieldDrafts` in `ResumeEditor.tsx`). This is strictly fewer network calls for the same
  outcome and doesn't change the debounce/coalescing contract `autosave.test.ts` verifies; flagging
  since the brief's phrasing ("Debounce ~500ms for text") could be read as per-field.
- **"Save PDF" button behavior**: the brief describes a home-page download button (built by T7,
  unchanged) and separately a "save button in the top right" that re-renders with current
  content/template. I implemented the editor's button to both `POST /pdf` (save the snapshot,
  updating `latestPdf` so the home page's download stays in sync) *and* immediately trigger the
  browser download (`GET /pdf`) in the same click, on the theory that a user clicking "Save PDF"
  while looking at the editor wants the file, not just a database write. If the intent was
  save-only (no browser download), that's a one-line change (drop the `downloadResumePdf` call) in
  `ResumeEditor.tsx`'s `handleDownload`.
- **Unselected items' order is not persisted**: dragging two *unselected* items relative to each
  other has no effect after the next render, because `orderForDisplay` always re-derives display
  order as "selected (in resume order), then unselected (in library order)" — there is nowhere to
  persist an order for content that isn't on the resume. This is a deliberate simplification
  (documented in `lib/editor/visibility.ts`'s docstring and covered by
  `visibility.test.ts`), not an oversight; only the selected subset of any drag ever hits the
  network.

## Known gaps / left for T9 or follow-up

- **No automated browser test of drag-and-drop itself.** This environment has no
  Playwright/Puppeteer installed, so the `@dnd-kit` interactions were verified by (a) unit-testing
  every piece of pure logic they depend on (`selections-reducer`, `visibility`,
  `autosave` — 44 cases total) and (b) manually issuing the exact `PUT /selections` bodies a real
  drag would produce and confirming round-trip persistence via curl (above). The DOM-level
  drag-and-drop wiring (`SortableList`/`SortableRow`) itself was not exercised in a real browser
  session beyond `npm run build`'s type/JSX checking and a manual look at the rendered page's RSC
  payload.
- **Template tab and live preview are placeholders**, by design — see
  `docs/agents/t8-seams.md` for the T9 handoff.
- **Optimistic archive/field edits don't roll back the UI on a failed save** — the local state
  update happens immediately (for responsiveness) and the network call is autosaved separately; on
  failure the header shows "Save failed — retry" and retrying resends the same (still-current)
  value, but the input itself is never reverted to its pre-edit value. Given the app is
  single-user and local-first by nature (no concurrent editors), this was judged an acceptable
  trade for responsiveness over strict optimistic-UI correctness; flagging in case a future task
  wants per-field rollback.
- **Resume renaming has no uniqueness or default-resume-name protection in the UI** — the API
  doesn't enforce either, so none was added client-side; not called out as a requirement.
