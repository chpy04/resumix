# T4 — Password gate

## What was built

- `lib/auth.ts` — mints and verifies the HMAC token. Web Crypto only
  (`crypto.subtle`), so it works identically in the Edge runtime (middleware)
  and the Node runtime (route handler, tests). Exports `login`, `mintToken`,
  `verifyToken`.
- `lib/auth-client.ts` — browser-side token storage (`localStorage['resumix.token']`)
  and `authedFetch`, a `fetch` wrapper that attaches `x-resumix-token` and, on a
  401, clears the token and dispatches a `resumix:auth-expired` window event.
- `middleware.ts` — guards `/api/:path*`, exempts `/api/auth` by pathname check,
  returns `401 { error: "unauthorized" }` JSON (never a redirect).
- `app/api/auth/route.ts` — `POST { password } -> { token }` / `401` on mismatch.
- `app/login/page.tsx` — the password screen (dark theme, Tailwind, uses the
  `--color-*` vars from `app/globals.css`). Exposes an optional `onSuccess`
  callback so it doubles as the inline form `AuthGate` renders.
- `components/AuthGate.tsx` — client component. Renders nothing until it has
  checked `localStorage` for a token (avoids a flash for already-authenticated
  users), then renders `LoginPage` or `children`. Listens for
  `resumix:auth-expired` to fall back to the login screen without a reload.
- `lib/auth.test.ts` — 11 unit tests (see verification output below).

Not touched: `app/layout.tsx`, `app/page.tsx` — T7 owns mounting `AuthGate`.

## Token format

`base64url(JSON.stringify({ v: 1, iat, exp })).base64url(hmac-sha256-signature)`

- `v` — format version, currently `1`. A future format bump can reject old
  tokens outright by checking this field.
- `iat` / `exp` — epoch milliseconds. Default TTL is 90 days
  (`DEFAULT_TTL_MS` in `lib/auth.ts`), matching the spec's "enter it once."
- The signature is an HMAC-SHA256 over the **base64url-encoded payload
  string** (not the decoded bytes), keyed by `AUTH_SECRET`. Any change to
  either half of the token — payload or signature — invalidates it.
- Verification checks, in order: two-part shape, signature match
  (timing-safe), JSON parse, `v === 1`, `Date.now() <= exp`.

Password and signature comparisons are timing-safe: both sides are hashed
with SHA-256 first (`sha256Hex`), then the resulting hex strings are compared
byte-by-byte with a constant-time XOR accumulator (`timingSafeEqualHex`).
This avoids `node:crypto`'s `timingSafeEqual` (unavailable on Edge) while
still not doing a short-circuiting `===` on secret-derived material.

## Threat model and its honest limits

This is a single-user convenience gate, not a security boundary suitable for
protecting data other people are trusted not to see:

- **It is a shared-secret bearer token, not a session.** Anyone who obtains
  the token (e.g. by reading `localStorage` via XSS, or physical access to
  the browser) has full API access for up to 90 days. There is no revocation
  list — the only way to invalidate a leaked token is to rotate `AUTH_SECRET`,
  which invalidates *every* outstanding token, including the legitimate one.
- **No rate limiting on `/api/auth`.** A long, high-entropy `APP_PASSWORD` is
  the only defense against brute force, per D-010's stated tradeoff. This is
  acceptable for a single-user hobby deployment but would not hold up against
  a targeted attacker with sustained access to the endpoint.
- **Timing-safety only covers the comparison step.** Hashing happens over the
  submitted value first, so the *comparison* doesn't leak byte-position
  information through timing, but this doesn't defend against, say,
  distinguishing "user exists" timing side channels elsewhere (not applicable
  here — single user) or network-level timing attacks.
- **Fail-closed on missing env, not fail-safe against misconfiguration
  elsewhere.** If `APP_PASSWORD`/`AUTH_SECRET` are unset, all logins and all
  token verifications are rejected and a clear error is logged server-side —
  but there's nothing stopping someone from deploying with `AUTH_SECRET`
  committed to source control or reused across environments. That's an
  operational discipline problem, not one this code can solve.
- **Middleware trusts the `x-resumix-token` header only.** There's no CSRF
  concern because there are no cookies involved — a third-party site cannot
  make the browser attach this header. The tradeoff (per D-002/D-010) is
  callers must be `fetch`, not a plain browser navigation, which is fine
  since this app doesn't do server-rendered authenticated pages.

## Deviations from the brief

- **`tsconfig.json`**: added `"allowImportingTsExtensions": true`. Node's
  native TypeScript execution (`node --experimental-strip-types`) requires
  relative import specifiers to include the real file extension
  (`./auth.ts`, not `./auth` or `./auth.js` — the latter doesn't resolve
  since no `.js` file exists). TypeScript 5.9 refuses to typecheck a `.ts`
  extension in an import specifier unless this flag is set; it's a no-op at
  the emit level since `noEmit` was already `true`, and no other file in the
  repo imports with an extension, so this has zero effect anywhere else
  today. Flagging it here since it's a shared config file outside T4's
  nominal file list, and future tasks writing `lib/**/*.test.ts` will rely on
  the same flag rather than rediscovering this.
- Everything else matches the brief as given (file list, token format,
  timing-safety, exempting `/api/auth`, fail-closed behavior, SSR guards,
  AuthGate not flashing, Enter-to-submit / error-clears-on-retype login UX).

## Notes for T6 / T7

- **T6** (API route handlers): nothing to do for auth — `middleware.ts`
  already guards every `/api/:path*` route except `/api/auth`. Route handlers
  don't need to check the token themselves.
- **T7** (home page / layout): mount `AuthGate` in `app/layout.tsx` wrapping
  `{children}`, since it's a client component that needs to run on every
  route. It renders `null` during its localStorage check, so no flash. Once
  mounted, use `authedFetch` from `lib/auth-client.ts` for all `/api/*` calls
  instead of raw `fetch` — that's what clears the token and drops back to the
  login screen on expiry/tamper. `POST /api/auth` itself should keep using
  plain `fetch` (it's exempt from the token check and doesn't have one yet).
- If either task needs to know whether an unmount/redirect-free "log out"
  action is wanted, `clearToken()` + dispatching a re-render (e.g. via
  `AuthGate`'s existing `resumix:auth-expired` listener, or a small refactor
  to expose a `logout()` helper) would be the natural extension — not built
  now since it wasn't requested.
