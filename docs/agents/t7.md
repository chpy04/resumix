# T7 — Home page

Branch: `feat/t7-home` (worktree `../resumix-wt/t7`). Not merged, not pushed.

## What was built

- `lib/fuzzy.ts` — a real subsequence-with-scoring fuzzy matcher (no
  dependency, no `includes()`). Uses a small DP over `(query length ×
  target length)` to find the *best-scoring* alignment of `query` as a
  subsequence of `target`, not just the first greedy one — this matters
  because a greedy left-to-right match can miss a much better word-boundary
  alignment later in the string. Scoring rewards contiguous runs, matches at
  a word boundary (start of string, after a separator, or a camelCase
  transition — read off the *original*-case target, not the lowercased one
  used for character comparison), matches at the very start of the string,
  and shorter targets as a tiebreak. Returns matched character positions
  too, for future highlighting, though the current UI doesn't use them yet.
  `fuzzyFilter(items, query, getText)` wraps this for a list, returning
  matches sorted best-first; an empty/whitespace-only query returns every
  item unscored in original order.
- `lib/fuzzy.test.ts` — 13 `node:test` cases: empty query/target, no-match,
  case-insensitivity, contiguous-beats-scattered (isolated from boundary
  effects), word-boundary-beats-mid-word, camelCase transitions, start
  beats later, shorter-target tiebreak, and `fuzzyFilter`'s sorting,
  empty-query passthrough, exclusion of non-matches, and ranking a
  whole-word match above a scattered one.
- `lib/api-client.ts` — the single place that knows the URL shapes from
  `docs/API.md`. Wraps `authedFetch` (never bare `fetch`) for:
  - `listResumes()` → `GET /api/resumes`
  - `createResume(name)` → `POST /api/resumes`
  - `deleteResume(id)` → `DELETE /api/resumes/:id` (exported per the task's
    file list; not wired into any UI yet — the spec's home-page
    requirements don't call for a delete affordance, so there's nothing to
    hook it up to. Left here for T8 or a future task.)
  - `downloadResumePdf(id)` → `GET /api/resumes/:id/pdf`, reads the filename
    from `Content-Disposition`, and triggers a client-side download via an
    object URL + a throwaway `<a download>`.
  Non-2xx responses throw `ApiError` (with `.status`), parsed from the
  documented `{ error: string }` body when present, else a generic
  "Request failed with status N" message. Components catch this and show
  readable text, never a blank page or an uncaught exception.
- `components/home/ResumeGrid.tsx` — owns all page state: fetch on mount
  (loading/error/ready), the search query, the new-resume dialog, and
  keyboard shortcuts (`/` and cmd+k focus search — `/` is ignored if focus
  is already in an input/textarea/contenteditable so it doesn't hijack
  typing elsewhere or in the search box itself). Splits the loaded list
  into the resume with `isDefault: true` (rendered once, pinned second) and
  everything else (rendered filtered/sorted, pinned New Resume card always
  first). Fuzzy search runs only over the non-default resumes, by `name`;
  the API's own ordering (default first, then `created_at desc`) is trusted
  for "newest first" when the query is empty, so no extra client-side sort
  is applied to the unfiltered list. Renders a skeleton grid while loading,
  a dismissable error panel with Retry on failure, and empty-state copy
  both for "no resumes at all" and "no resumes match this search."
- `components/home/ResumeCard.tsx` — the whole card is a `role="button"`
  navigating to `/resume/<id>` (click or Enter/Space), showing `name`
  ("company name" per spec — see assumption below) and a formatted
  `createdAt`. No PDF thumbnail, per the spec's explicit "that would be
  basically useless." The Default card gets an accent border, a "Default"
  badge, and a slightly different background. The download button is a
  separate element that calls `event.stopPropagation()` before doing
  anything, so it never also triggers the card's navigation; it's disabled
  with a `title` tooltip when `latestPdf` is `null`, shows a spinner while
  in flight, and surfaces a download error inline on the card without
  crashing anything else.
- `components/home/NewResumeCard.tsx` — the pinned, always-first blank card
  that opens the dialog.
- `components/home/NewResumeDialog.tsx` — a real in-app modal (backdrop +
  `role="dialog"`), not `window.prompt()`. Autofocuses its input on open,
  closes on Escape or backdrop click, submits on Enter via the form's
  `onSubmit` (native behavior, no bespoke keydown handling needed for
  Enter), and disables its controls while the create request is in flight.
- `components/home/SearchBox.tsx` — the search input, exposing a
  `forwardRef` so `ResumeGrid` can focus it from the keyboard shortcut
  handler. Shows a `/` hint in the corner.
- `app/page.tsx` — now `<AuthGate><ResumeGrid /></AuthGate>`, replacing the
  scaffold placeholder.

### Unplanned but necessary: fixed a pre-existing build break from T4

`npm run build` failed on a clean checkout of `main` (confirmed by
stashing all my changes and rebuilding — same failure, so this predates
T7 entirely): `app/login/page.tsx`'s default export took an `onSuccess`
prop so `components/AuthGate.tsx` could reuse it inline. Next 15 generates
a `PageProps` type (`{ params?, searchParams? }`) for every `page.tsx` and
checks the default export's prop type against it; TypeScript's "weak type
detection" rejects `{ onSuccess?: () => void }` because it has *zero*
properties in common with `PageProps`, even though every field involved is
optional (`TS2559`). I also found that a `page.tsx` module can't have any
other named export Next doesn't recognize (tried exporting the form as a
named export alongside the default — `TS2344`, "does not satisfy the
constraint").

Fix: extracted the form itself into `components/LoginForm.tsx` (identical
implementation, just moved), made `app/login/page.tsx` a zero-prop
wrapper (`export default function LoginPage() { return <LoginForm />; }`),
and pointed `components/AuthGate.tsx` at `components/LoginForm` instead of
`app/login/page`. No behavior change — same component tree, same props,
same login flow. This was necessary because `npm run build` is a required
verification step for T7 and was unconditionally broken without it.
Flagging clearly here since these two files aren't in T7's owned-files
list.

## Assumptions about API response shapes (please check on integration)

- `ResumeSummary.name` is what the card displays as "company name." The
  spec's home-page bullet says cards show "the company name," but
  `docs/API.md`'s `ResumeSummary` only has `name` (no separate `company`
  field), and `POST /api/resumes` takes `{ name }` for what the dialog
  calls "company name." I'm treating `resume.name` as the company name
  end-to-end. If T6 or the DB schema end up distinguishing a resume's
  display name from a company field, the card and dialog will need an
  update to point at the right field.
- `GET /api/resumes` is assumed to always include at most one
  `isDefault: true` entry, per the DB's partial unique index
  (`ux_resume_one_default`, per T1's report). `ResumeGrid` degrades
  gracefully if there are zero (just doesn't render a Default card) but
  doesn't specifically handle more than one — it would just render the
  first match as the pinned Default and let the rest fall through to the
  regular grid, silently.
- `GET /api/resumes/:id/pdf`'s `Content-Disposition` header is assumed to
  always include a `filename="..."` (quoted) or `filename=...` (bare)
  parameter that `authedFetch`'s caller can read via
  `response.headers.get('content-disposition')`. If the real route ever
  omits it (e.g., on some error path that still returns 200), the
  download falls back to `resume-<id>.pdf` rather than throwing.
- Error responses are assumed to always be `{ "error": "message" }` JSON
  per `docs/API.md`'s contract, on every non-2xx status including 404 and
  500. `parseErrorMessage()` falls back to a generic
  "Request failed with status N" if the body isn't JSON or doesn't have an
  `error` string, so a malformed error body degrades gracefully rather
  than crashing, but the *readable* message the spec asks for depends on
  T6 actually following this shape.
- `POST /api/resumes` is assumed to return a full `ResumeSummary` (not
  just an id) so the redirect target and any immediate UI update have
  everything they need without a second round trip — this matches
  `docs/API.md`'s documented return type.
- 204 on `DELETE /api/resumes/:id` — `api-client.ts`'s `requestJson` special
  -cases status 204 to skip `response.json()` (which would throw on an
  empty body). Untested against a real server since delete isn't wired
  into the UI yet.

## Deviations from the spec / task instructions

- Fixed `app/login/page.tsx` and `components/AuthGate.tsx` (outside T7's
  owned-files list) to unblock `npm run build`, which was broken on `main`
  before T7 touched anything. See the "Unplanned but necessary" section

  integrator wants to review or re-attribute that specific change.
- `deleteResume` exists in `lib/api-client.ts` per the task's explicit file
  list ("resumes list/create/delete/pdf-download") but isn't wired into any
  home-page UI, since neither the spec bullet nor the requirements list
  for T7 asks for a delete affordance on the grid. Left as a typed,
  ready-to-use export.
- Could not visually verify the page in an actual browser (see "Manual
  smoke test" above) — no Playwright/Puppeteer/Chrome available in this
  environment. Verified via SSR HTML output, direct API stubbing +
  `curl`, and unit tests instead. Worth a real click-through once the
  environment supports it or once T6's real API is up.
- `fuzzyScore`'s DP is O(query.length × target.length) per item, run over
  every resume on every keystroke. Fine at any realistic resume count
  (dozens, maybe low hundreds), but if this ever needs to scale to
  thousands of resumes it'd be worth memoizing per-target or debouncing
  the search input — not done here since it wasn't asked for and the
  current scale doesn't need it.
