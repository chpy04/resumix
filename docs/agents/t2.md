# T2 — LaTeX compile service

## What was built

- `services/latex/server.js` — a zero-dependency `node:http` server that
  implements the frozen contract in `docs/API.md` ("Latex service"):
  `POST /compile { tex }` -> `{ ok, pdfBase64?, pages, errors, log,
  durationMs }`, `GET /health` -> `{ ok: true }`.
  - Fresh `mkdtemp` working directory per request; removed in a `finally`
    (success, failure, or timeout).
  - Runs `pdflatex -interaction=nonstopmode -halt-on-error
    -file-line-error -no-shell-escape`, with `SOURCE_DATE_EPOCH=0` /
    `FORCE_SOURCE_DATE=1` for byte-reproducible output, and an isolated
    `HOME`/`TEXMFVAR`/`TEXMFHOME`/`TEXMFCONFIG` pointed inside that temp
    dir so a non-root user never needs write access anywhere else.
  - Prefers the `.log` file over captured stdout/stderr. Parses page count
    from `Output written on ... (N pages, ...)` and errors from lines
    starting with `!` **or** `-file-line-error`'s `path:line:` prefix
    (both occur depending on the error type), each paired with its
    following `l.NNN` context line when present.
  - Hard 20s timeout (`LATEX_COMPILE_TIMEOUT_MS`, default `20000`) that
    `SIGKILL`s the child; timeout still yields a normal `200 {ok:false}`
    response, not a hang.
  - Request body capped at 2MB (`LATEX_MAX_BODY_BYTES`) -> `400` if
    exceeded (checked via `Content-Length` up front and again while
    streaming, in case the header lies).
  - Bounded concurrency (`LATEX_MAX_CONCURRENCY`, default `2`) with a
    bounded wait queue (`LATEX_MAX_QUEUE`, default `8`); once both are
    full, extra requests get `503` instead of spawning more `pdflatex`
    processes.
  - `200` for both compile success and compile failure (`ok: true`/`false`
    respectively) — a bad `.tex` is a normal, renderable result, not a
    transport error. `400` for malformed requests (bad JSON, missing/empty
    `tex`, oversized body). `500` only for genuine service faults (e.g.
    `pdflatex` binary missing). `503` for "busy, try later."
- `services/latex/Dockerfile` — `debian:bookworm-slim` +
  `texlive-latex-base`, `texlive-latex-recommended`, `texlive-latex-extra`,
  `texlive-fonts-recommended`, `texlive-plain-generic`, Debian's `nodejs`
  package (v18, has global `fetch` for the compose healthcheck). Runs as a
  non-root user `latex` (uid 10001), has a `HEALTHCHECK` hitting
  `/health`. No `npm install` step — `server.js` has zero dependencies.
- `services/latex/README.md` — build/run/deploy instructions, env var
  reference, and a security section (`-no-shell-escape`, non-root,
  "never expose this publicly").
- `lib/latex.ts` — typed Next.js-side client: `compileTex(tex, opts?)`
  hitting `${LATEX_SERVICE_URL}/compile`, with a 25s fetch timeout
  (`AbortController`) and a `LatexServiceError` that gives a clear message
  ("Could not reach the latex service. Is the 'latex' container running?
  (docker compose up -d latex)") instead of a raw fetch/TypeError bubbling
  to the UI. Note: this is a purpose-built type (`LatexCompileResult`), not
  a reuse of `lib/types.ts`'s `RenderResult` — the service contract has no
  `warnings` field and does have `durationMs`; `RenderResult` is the
  higher-level `/api/resumes/:id/render` shape that the (future) route
  handler will build by combining this with renderer-level warnings.

## Deviations from the contract

- **Express -> `node:http`.** `docs/ARCHITECTURE.md` describes the service
  as "TeX Live + Express `/compile`". Per the task instructions, this was
  built as a dependency-free `node:http` server instead — same HTTP
  contract, smaller image, no `npm install` layer. Documented in
  `services/latex/README.md`.
- `503 { error }` is returned when the concurrency queue is full. Not
  mentioned in `docs/API.md`, but necessary to satisfy "cap concurrency ...
  a burst of preview requests cannot fork-bomb the container" without
  silently dropping or hanging requests. `200`/`400`/`500` all behave
  exactly as specified.

## Fly.io deployment notes (details in `services/latex/README.md`)

- Deploy `services/latex` as its own Fly app (`fly launch` from that
  directory), separate from the Next.js app.
- `internal_port = 8080` in `fly.toml`, matching the Dockerfile's
  `EXPOSE 8080`.
- Reach it only over Fly's private networking (`*.internal` / Flycast),
  never the public edge — this service has no auth of its own and must
  sit behind the Next.js app per the security note in the task and in
  `services/latex/README.md`.
- No volume needed; everything is per-request temp state, deleted after
  each compile.
- Set the Next.js app's `LATEX_SERVICE_URL` to the Fly private address
  (e.g. `http://resumix-latex.internal:8080`).
