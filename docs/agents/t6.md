# T6 — API route handlers

## What was built

Every endpoint in `docs/API.md` except `POST /api/auth` (pre-existing, untouched), split into
a thin `app/api/**/route.ts` layer and a `lib/queries/**` data-access layer, per the task brief.

### Files added

- `lib/http.ts` — shared route-handler plumbing: `parseJsonBody(request, zodSchema)` (throws
  `BadRequestError` on invalid JSON or a failed schema check) and `withApiErrors(handler)` (maps
  `BadRequestError` → 400, `NotFoundError` → 404, anything else → 500 with a generic message,
  logged server-side, never a raw stack trace to the client).
- `lib/validation.ts` — every zod request-body schema (one per endpoint that takes a body).
- `lib/filename.ts` + `lib/filename.test.ts` — `buildResumeFilename(resumeName, prefix?)` →
  `<prefix>_<Company>_Resume.pdf`. Pure, 14 `node:test` cases.
- `lib/storage.ts` — the PDF snapshot adapter (D-003): `saveResumePdfSnapshot`,
  `getLatestResumePdfSnapshot`, `getLatestResumePdfMetaByResumeId` (batched, no per-resume
  N+1 for `GET /api/resumes`' `latestPdf` field, via `selectDistinctOn`). Everything that knows
  the bytes live in a `bytea` column is confined to this one file.
- `lib/queries/errors.ts` — `NotFoundError` / `BadRequestError`, the only two query-layer error
  types; `lib/http.ts` maps them to status codes.
- `lib/queries/templates.ts`, `experiences.ts`, `experience-bullets.ts`, `projects.ts`,
  `project-bullets.ts`, `skill-rows.ts`, `skills.ts` — CRUD (create/update; no delete, D-011) for
  each content type.
- `lib/queries/library.ts` — `assembleLibrary(includeArchived)`: a handful of flat queries
  (one per content table, one per bullet/skill table) plus in-memory grouping by parent id — no
  per-row lookups.
- `lib/queries/selections.ts` — `getSelections(resumeId)` and `replaceSelections(resumeId,
  Partial<Selections>)`, the autosave target. Six explicit per-slice replace functions (not one
  generic helper — the six bridge tables don't share a Drizzle table shape, and a generic
  attempt fought the type system for no benefit); all six run inside a single
  `db.transaction`, and every id (and, for bullets/skills, parent linkage) is validated against
  the content tables *before* the delete+insert, so an invalid id throws `BadRequestError` and
  rolls back the whole PUT rather than writing a dangling row.
- `lib/queries/resumes.ts` — `listResumeSummaries`, `createResume` (clones the default resume's
  template + all six selection slices via `cloneSelections`), `updateResume`, `deleteResume`
  (400s on the default resume), `getResumeDetail` (the one-round-trip editor payload, D-012;
  library is always fetched with `includeArchived: true` here — the editor UI filters it).
- `lib/queries/render.ts` — `renderResumeById(resumeId, templateOverride?)`: assembles
  `{ templateContent, library, selections }` and calls T3's `renderResume`. Pure DB read; no
  LaTeX compilation (that's in the route handlers, which call T2's `compileTex`).
- `app/api/**/route.ts` — 19 new route files (list below).
- `lib/queries/test-fixtures.ts`, `lib/queries/selections.test.ts`, `resumes.test.ts`,
  `library.test.ts` — integration tests against a real Postgres.

## Deviations / contract ambiguities resolved

1. **`PUT /selections` return body.** The contract's table for this endpoint has no "returns"
   column at all (every other table in `docs/API.md` has one). I resolved this by returning the
   full, freshly-read `Selections` for the resume — cheap (it's the same query `GET
   /resumes/:id` already does for that slice) and gives the autosave caller a way to confirm
   server state without a second round trip. If T7/T8 would rather have a bare `204`, this is a
   one-line change in `app/api/resumes/[id]/selections/route.ts`.
2. **`POST /resumes/:id/pdf` on a LaTeX compile failure.** The contract says this endpoint
   "renders, stores a `resume_pdf` snapshot" and returns `{ filename, createdAt }` — but says
   nothing about what happens when the compile fails, and there is no PDF to name or store in
   that case. I made it mirror `/render`'s shape instead: `200 { ok: false, pages, errors,
   warnings, log }`, storing nothing, vs. `200 { ok: true, filename, createdAt }` on success.
   This keeps the "LaTeX failure is never a 500" rule uniform across both rendering endpoints.
   Flagging this explicitly for T7/T8 since it's an added `ok` field beyond the literal contract
   text.
3. **Filename source.** `docs/SCHEMA.md` says `resume_pdf.filename` is
   `Chris_Pyle_<Company>_Resume.pdf`, but there is no `company` column anywhere in the schema —
   `resume` only has `name`. I used the resume's own `name` as "Company", which is exactly
   consistent with the task brief's own worked example (`POST /resumes { name: "google cloud"
   }` → `Chris_Pyle_Google_Cloud_Resume.pdf`).
4. **`GET /api/resumes/:id` library archived-ness.** Per the task brief ("Include archived
   content in the library... `GET /api/library` honours `?includeArchived=1`"), the resume
   detail endpoint always calls `assembleLibrary(true)` regardless of query params — there's no
   `?includeArchived` on that route; only the standalone `/api/library` respects the flag.
5. **A real bug I found and fixed via manual verification** (not a contract ambiguity, but worth
   flagging): my first cut of `lib/queries/library.ts` filtered archived rows on the parent
   table (`experience`, `project`, `technical_skill_row`) but not on the **child** table
   (`experience_bullet`, `project_bullet`, `technical_skill`) when `includeArchived` is false —
   so an archived bullet under a non-archived experience leaked into `GET /api/library`'s
   default (unfiltered) response. Fixed by adding the same `isArchived` filter at the bullet/
   skill level; added a regression test
   (`lib/queries/library.test.ts`: "an archived bullet under a non-archived parent is excluded
   by default, included with includeArchived=true"). Caught during the manual curl lifecycle
   test below, not by the unit tests I'd originally written — worth double-checking if T7/T8
   build any other cross-cutting archive logic.

## Notes for T7 / T8 / T9

- **T7 (frontend, `lib/api-client.ts`)**: `PUT /selections` returns the full `Selections`
  object (see Deviations #1) — useful if you want to reconcile local optimistic state after a
  debounced save, but you can also ignore the body and treat any 2xx as success.
  `POST /resumes/:id/pdf` returns `{ ok: true, filename, createdAt } | { ok: false, pages,
  errors, warnings, log }` (Deviations #2) — check `ok` before reading `filename`.
- **Auth**: nothing to do — `middleware.ts` (T4) already guards every route under `/api/*`
  except `/api/auth`; every handler here assumes a valid request already got past it.
- **`GET /api/resumes/:id/pdf`** never renders on the fly — it 404s if `POST /pdf` was never
  called for that resume. If the UI wants "always show *a* PDF," it needs to call `POST /pdf`
  itself first (e.g. on first load of a resume with no snapshot yet), not fall back to `/render`.
- **Ordering contract**: every array in `Selections` is authoritative order — `sort_order` is
  never something a client computes; the server always derives it from array index on `PUT
  /selections`, and `GET`s always return arrays already in `sort_order asc`.
- **Everything is validated server-side** with zod (`lib/validation.ts`); 400s carry a
  human-readable `{ error }` message including the offending field name where available (e.g.
  `"name: Invalid input: expected string, received undefined"`), safe to show directly or map
  to a friendlier string.
- If a future task adds more content-table archive interactions, double-check both the parent
  *and* the child are filtered by `isArchived` in `lib/queries/library.ts` when
  `includeArchived` is false — see Deviations #5, the one real bug this task found and fixed.
